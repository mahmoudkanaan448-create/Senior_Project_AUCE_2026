[21|Heading 1] Abstract
[23|Normal] Cyberattacks have become more sophisticated as organizations depend increasingly on cloud computing, IoT devices, web systems, and high-speed networks. Traditional signature-based Intrusion Detection Systems are useful for known attacks, but they are limited when attackers modify their behavior or when unknown zero-day attacks appear. This project proposes an AI-Powered Network Traffic Analyzer & Anomaly Detector, an academic Network Detection and Response platform designed to capture network traffic, extract meaningful features, detect anomalies, classify known attacks, generate alerts, and support automated response.

[139|Heading 2] 1.1 Background
[140|Normal] Modern computer networks generate huge volumes of packets every second. These packets carry normal business activity, web requests, cloud communication, authentication traffic, database connections, and sometimes malicious behavior. Because the number of packets is too large for manual inspection, organizations need automated monitoring systems that can discover suspicious behavior quickly and accurately.
[141|Normal] Traditional IDS tools usually depend on predefined signatures. This approach is effective when the attack is already known, but it becomes weaker when the attack is new, modified, hidden inside normal-looking behavior, or performed slowly over time. Artificial Intelligence provides an alternative approach because it can learn patterns from network features and detect behavior that does not match normal traffic.
[142|Heading 2] 1.2 Problem Statement
[143|Normal] The main problem addressed by this project is the difficulty of detecting known and unknown attacks in large-scale network traffic. Security analysts may receive many alerts, and traditional systems can miss unknown attacks or generate false positives. Therefore, the project proposes a hybrid AI-based platform that can analyze flows, classify attacks, detect anomalies, and present understandable alerts to the administrator.
[144|Heading 2] 1.3 Proposed Solution
[145|List Bullet] Capture network traffic from live interfaces, PCAP files, or benchmark datasets.
[146|List Bullet] Extract flow-based features such as duration, bytes, packets, protocol, ports, packet length statistics, and rate values.
[147|List Bullet] Preprocess the data by cleaning missing values, encoding categorical values, and scaling numerical features.
[148|List Bullet] Use multiple AI models for known attack detection, anomaly detection, and prediction.
[149|List Bullet] Provide Explainable AI outputs, Threat Intelligence enrichment, automatic response, and dashboard visualization.

[160|Heading 2] 2.1 Traditional Intrusion Detection Systems
[161|Normal] An Intrusion Detection System monitors network or host activity to discover suspicious behavior. Signature-based detection compares traffic with known attack patterns and is efficient for known threats. However, it cannot reliably identify new attacks. Anomaly-based detection learns normal behavior and alerts when traffic deviates from that baseline. Hybrid IDS combines both methods to improve coverage.
[162|Heading 2] 2.2 AI-Based Intrusion Detection
[163|Normal] AI-based IDS uses Machine Learning and Deep Learning to recognize patterns in network traffic. Supervised learning models use labeled datasets to classify traffic as normal or malicious. Unsupervised learning models detect outliers without requiring labels. Deep Learning models can learn complex relationships and sequential behavior, especially when network activity changes over time.

[264|Heading 2] 4.4 Decision Fusion
[265|Normal] The proposed system does not depend on one model only. Instead, it combines model outputs into a final risk score. For example, if XGBoost classifies a flow as attack, Isolation Forest marks it as outlier, and Threat Intelligence reports the IP as suspicious, the system increases the severity level. This fusion approach is expected to reduce false negatives and improve analyst confidence.

[354|Heading 1] Chapter 7 - Practical Implementation Notes
[355|Heading 2] 7.1 Dataset Preparation Notes
[356|Normal] Dataset preparation is one of the most important stages in this project. Intrusion detection datasets may contain missing values, infinite values, duplicated records, imbalanced classes, and features that do not exist in real live traffic. Therefore, the preprocessing pipeline must be written carefully and reused during real-time prediction. A common mistake is to train the model with one set of features and then send a different set of features during live detection. To avoid this issue, the final feature list should be saved and used consistently.
[357|Heading 2] 7.2 Handling Class Imbalance
[358|Normal] Network intrusion datasets are often imbalanced. Normal traffic may dominate the dataset, or one attack type may appear more frequently than the others. If the model is evaluated only using accuracy, it may appear successful while ignoring rare attacks. Therefore, this project uses precision, recall, F1-score, confusion matrix, and ROC-AUC. For stronger implementation, class weights, stratified splitting, undersampling, or oversampling can be tested.
[359|Heading 2] 7.3 Threshold Tuning
[360|Normal] The anomaly detection threshold directly affects false positives and false negatives. A low threshold may generate too many alerts, while a high threshold may miss attacks. The project should test several thresholds and select the one that gives an acceptable balance between detection and alert fatigue. In real cybersecurity environments, thresholds may also differ based on asset importance and business risk.
[361|Heading 2] 7.4 Explainability Strategy
[362|Normal] Explainable AI is included because security administrators need to understand why an alert was created. For tree-based models, feature importance can explain which features had the strongest influence during training. For individual predictions, SHAP-style explanation can show which values increased the risk score. In the Bachelor prototype, feature importance and a simple reason message are enough to demonstrate the concept.
[363|Heading 2] 7.5 Report Generation
[364|Normal] The report generation module should summarize alert ID, timestamp, source IP, destination IP, protocol, predicted class, confidence, threat score, Threat Intelligence result, recommended action, and response status. The report can be exported as PDF or CSV. This feature is important because it proves that the system can support documentation and incident review, not only display alerts.

[378|Heading 2] 8.1 Starting the System
[379|Normal] The administrator starts the database service, then starts the FastAPI backend, then opens the dashboard in the browser. [380|Heading 2] 8.2 Uploading Data or Capturing Live Traffic
[381|Normal] The system supports two operating modes. In dataset mode, the administrator uploads a CSV file extracted from a dataset such as CICIDS2017. In live mode, the capture module collects packets from a selected network interface and converts them into flow features. Dataset mode is easier for training and evaluation, while live mode is better for demonstration.
[382|Heading 2] 8.3 Reading the Dashboard
[383|Normal] The dashboard should be interpreted carefully. A high threat score does not always mean a confirmed attack; it means the traffic is suspicious and needs attention. The administrator should check the predicted class, confidence score, source IP, destination IP, protocol, model explanation, and Threat Intelligence result before taking final action.
[384|Heading 2] 8.4 Responding to Alerts
[385|Normal] When an alert appears, the administrator can review details, mark the alert as investigated, export a report, or block the source IP. In the academic prototype, IP blocking may be simulated by storing the IP in the blocked_ips table. In a real deployment, this action can be connected to firewall rules only after careful testing and approval.
